Three files, none of them long. What makes the page worth reading slowly is that each one is shaped by a decision Baseline made on your behalf, and the reasons are what stop the shapes looking arbitrary later.

---

## Add the plugin

The config file is short, and its last line is the strangest thing in the whole tutorial. Create `eleventy.config.js` in the project root:

```js
import baseline, { config as baselineConfig } from '@apleasantview/eleventy-plugin-baseline';
import settings from './src/_data/settings.js';

/** @param {import("@11ty/eleventy").UserConfig} eleventyConfig */
export default async function (eleventyConfig) {
	await eleventyConfig.addPlugin(baseline(settings));
}

export const config = baselineConfig;
```

`baseline()` takes two arguments: `settings` and `options`. Settings is what your site *is*, options is how Baseline *behaves*. Keeping them apart means you can rename your site without going near the module configuration, and switch a module off without touching your site's identity. Here you pass settings only, which leaves every option at its default: `sitemap` on, `multilingual` off, `navigator` on in development and off in production. That is the set this tutorial wants.

Now that last line, because the obvious question is why a plugin cannot set up its own directories.

It is a timing problem. Eleventy reads its directory configuration before it loads any plugin, so by the time `addPlugin()` runs the decision is already made and nothing inside the plugin can reach back and change it. Baseline ships those directories as a separate export instead and asks you to forward it. That one line is what makes `src/` the input, `dist/` the output, and the folders you laid out on the last page findable by name. Leave it off and Baseline still runs, badly, in a project it cannot see.

The [[config-export | config export reference]] has the longer version, if you want it.

## Give the site its identity

Next, the file `eleventy.config.js` just imported. Create `src/_data/settings.js`:

```js
export default {
	title: 'Simple Baseline Site',
	tagline: 'Hello, Eleventy + Baseline',
	url: process.env.URL,
	defaultLanguage: 'en',
	noindex: false,

	head: {
		link: [{ rel: 'stylesheet', href: '/assets/css/index.css' }],
		script: [{ src: '/assets/js/index.js', defer: true }],
		meta: [{ name: 'color-scheme', content: 'light dark' }]
	}
};
```

Being a real file rather than an object typed into the config is the whole point. It sits in `src/_data/`, which means Eleventy also picks it up as global data, and every template can read `settings.title` without importing anything. One definition, two audiences: the plugin and your pages.

What belongs in here is identity, the things that would still be true if you rewrote every template tomorrow. `title` composes the `<title>` tag and becomes `og:site_name`. `tagline` fills in as a description where a page has not written its own. `defaultLanguage` sets the `lang` attribute. `noindex` is the site-wide switch for keeping a staging build out of search results, and it is off here because this site is imaginary and nobody is looking for it.

The `head` block is how tags reach every page. `link`, `script` and `meta` are arrays, each entry's keys become the attributes on the rendered tag, and they arrive alongside what Baseline emits anyway: charset, viewport, title, description, canonical, robots. One stylesheet, one script, one colour-scheme hint is enough to start with. The two files those paths point at get written two pages from now.

{% alertBlock "info" %}

Baseline compiles your CSS and JS, but it does not link them for you. A bundle that is not listed here gets built and then never loaded, which looks exactly like the stylesheet not working.

{% endalertBlock %}

## Tell it where it lives

One value in that file changes depending on where the site is running, which is why `url` reads from the environment instead of being typed in. Create a `.env` in the project root:

```text
ELEVENTY_ENV="development"
URL="http://localhost:8080/"
```

Baseline loads `dotenv` itself, so both variables are available in `eleventy.config.js` and `settings.js` with no setup on your part.

`URL` becomes `settings.url`, and `settings.url` is the only place Baseline looks. Everything absolute it emits is anchored there: the canonical link on every page, every entry in the sitemap, the structured data, and the links inside your pages once Eleventy resolves them. Get it wrong and nothing looks broken, which is the annoying part. The site works perfectly and tells search engines it lives on your laptop.

Leave it unset and Baseline says so at startup, then leaves the canonical links out rather than publishing one it had to guess. No claim beats a wrong claim.

`ELEVENTY_ENV` is the development-versus-production switch. Set to `production` it minifies your CSS and drops the navigator page; the `build` script sets it for you, which is what `cross-env` was installed for. On a deployed site both variables come from your host rather than from this file, which is why the file stays out of git.

Eleventy will start now. It will also render nothing at all, because there is still no content. That is the next page.
