Three files, none of them long. Each one is shaped by a decision Baseline already made, and knowing which decision keeps the shapes from looking arbitrary later.

---

## Add the plugin

The config file is short, and its last line is the strangest thing in the whole tutorial. Create `eleventy.config.js` in the project root:

```js
import baseline, { config as baselineConfig } from '@apleasantview/eleventy-plugin-baseline';
import settings from './src/_data/settings.js';

/** @param {import("@11ty/eleventy").UserConfig} eleventyConfig */
export default async function (eleventyConfig) {
	await eleventyConfig.addPlugin(baseline(settings));
}

export const config = baselineConfig;
```

`baseline()` takes two arguments: `settings`, which is what your site *is*, and `options`, which is how Baseline *behaves*. Here you pass settings only, which leaves every option at its default: `sitemap` on, `multilingual` off, `navigator` on in development and off in production. That is the set this tutorial wants.

Now that last line. Eleventy reads its directory configuration before it loads any plugin, so Baseline cannot set its own. It ships them as a separate export and asks you to forward it. That one line is what makes `src/` the input, `dist/` the output, and the folders you laid out on the last page findable by name. Leave it off and Baseline still runs, badly, in a project it cannot see.

Why the timing works out that way is the [[config-export | config export reference]]'s job.

## Give the site its identity

Next, the file `eleventy.config.js` just imported. Create `src/_data/settings.js`:

```js
import 'dotenv/config';

export default {
	title: 'Simple Baseline Site',
	tagline: 'Hello, Eleventy + Baseline',
	url: process.env.BASELINE_URL,
	defaultLanguage: 'en',
	noindex: false,

	head: {
		link: [{ rel: 'stylesheet', href: '/assets/css/index.css' }],
		script: [{ src: '/assets/js/index.js', defer: true }],
		meta: [{ name: 'color-scheme', content: 'light dark' }]
	}
};
```

It is a real file rather than an object typed into the config, and it sits in `src/_data/`, which means Eleventy also picks it up as global data, and every template can read `settings.title` without importing anything. One definition, two audiences: the plugin and your pages.

What belongs in here is identity, the things that would still be true if you rewrote every template tomorrow. `title` and `tagline` both feed the `<title>` tag, the tagline turning up on the homepage where there is no page title to lead with. `defaultLanguage` sets the `lang` attribute, and `noindex` is the site-wide switch for keeping a staging build out of search results. It is off here because this site is imaginary and nobody is looking for it. There are more keys than these, and the [[site-settings | settings reference]] has them all.

The `head` block is how tags reach every page. `link`, `script` and `meta` are arrays, and each entry's keys become the attributes on the rendered tag. They arrive alongside what Baseline emits anyway, which the [[head | head module]] lists in full. One stylesheet, one script, one colour-scheme hint is enough to start with; the two files those paths point at get written two pages from now.

{% alertBlock "info" %}

Baseline compiles your CSS and JS, but it does not link them for you. A bundle that is not listed here gets built and then never loaded, which looks exactly like the stylesheet not working.

{% endalertBlock %}

## Tell it where it lives

One value in that file changes depending on where the site is running, which is why `url` reads from the environment instead of being typed in. Create a `.env` in the project root:

```text
ELEVENTY_ENV="development"
BASELINE_URL="http://localhost:8080/"
```

A `.env` file does not load itself, so install the package that does it:

```bash
npm install dotenv
```

That is the line at the top of `settings.js`. It sits in that file rather than in the config on purpose: the file that reads an environment variable is the one that should load the environment, and then it works whatever imported it, in whatever order. Baseline itself does not need the package. The `.env` does, and a project that sets its variables in npm scripts or on its host wants neither.

`BASELINE_URL` becomes `settings.url`, and `settings.url` is the only place Baseline looks when it needs an absolute URL. Localhost is the honest answer while you are working on your laptop; the value starts to matter when you build for production, two pages from now.

Leave it unset and Baseline says so at startup, then leaves the canonical links out rather than publishing one it had to guess. No claim beats a wrong claim.

`ELEVENTY_ENV` is the development-versus-production switch, and what it actually changes belongs to that same page. On a deployed site both variables come from your host rather than from this file, which is why the file stays out of git.

Eleventy will start now. It will also render nothing at all, because there is still no content. That is the next page.
