Three files, and none of them is long. What makes this page worth reading slowly is that each one is shaped by a decision Baseline made on your behalf, and knowing the reason is what stops the shapes looking arbitrary later.

---

## Add the plugin

Create `eleventy.config.js` in the project root:

```js
import baseline, { config as baselineConfig } from '@apleasantview/eleventy-plugin-baseline';
import settings from './src/_data/settings.js';

/** @param {import("@11ty/eleventy").UserConfig} eleventyConfig */
export default async function (eleventyConfig) {
	await eleventyConfig.addPlugin(baseline(settings));
}

export const config = baselineConfig;
```

`baseline()` takes two arguments: `settings` and `options`. Settings is what your site *is*, options is how Baseline *behaves*. Keeping them apart means you can rename your site without going near the module configuration, and turn a module off without touching your site's identity. Here you pass settings only, which leaves every option at its default: `sitemap` on, `multilingual` off, `navigator` on in development and off in production. That's the set this tutorial wants.

The last line is the strange one, and it's worth a moment because nothing else in the Eleventy ecosystem looks like it.

Eleventy reads its directory configuration before it loads any plugin, so by the time `addPlugin()` runs it has already decided where input and output live. A plugin cannot reach back and change that. Baseline ships those directories as a separate export instead and asks you to forward it, which is what makes `src/` the input, `dist/` the output, and the folders you laid out on the previous page findable by name. Leave the line off and Baseline runs, badly, in a project it can't see. The [[config-export | config export reference]] has the longer version.

## Give the site its identity

Create `src/_data/settings.js`:

```js
export default {
	title: 'Simple Baseline Site',
	tagline: 'Hello, Eleventy + Baseline',
	url: process.env.URL || 'http://localhost:8080/',
	defaultLanguage: 'en',
	noindex: false,

	head: {
		link: [{ rel: 'stylesheet', href: '/assets/css/index.css' }],
		script: [{ src: '/assets/js/index.js', defer: true }],
		meta: [{ name: 'color-scheme', content: 'light dark' }]
	}
};
```

This is the file `eleventy.config.js` imported a moment ago, which is the whole reason it exists as a file rather than an object typed inline. It sits in `src/_data/` so Eleventy picks it up as global data too, and every template can read `settings.title` without importing anything. One definition, two audiences: the plugin and your pages.

What lands in here is identity, the things that would still be true if you rewrote every template tomorrow. `title` composes the `<title>` tag and becomes `og:site_name`. `tagline` fills in as a description where a page hasn't written its own. `defaultLanguage` sets the `lang` attribute. `noindex` is the site-wide switch for keeping a staging build out of search results, and it is off here because this site is imaginary and nobody is looking.

The `head` block is how you add tags to every page. `link`, `script` and `meta` are arrays, each entry's keys become the attributes on the rendered tag, and they arrive alongside what Baseline emits by default: charset, viewport, title, description, canonical, robots. One stylesheet, one script, one colour-scheme hint is enough to get started, and the two files they point at get written two pages from now.

{% alertBlock "info" %}

Baseline compiles your CSS and JS, but it does not link them for you. If a bundle is not listed here, it is built and then never loaded, which looks exactly like the stylesheet not working.

{% endalertBlock %}

## Tell it where it lives

`url` is the one value in there that changes depending on where the site is running, which is why it reads from the environment rather than being typed in. Create a `.env` file in the project root:

```text
ELEVENTY_ENV="development"
URL="http://localhost:8080/"
```

Baseline loads `dotenv` itself, so both variables are available in `eleventy.config.js` and `settings.js` without any setup on your part.

`URL` does two jobs at once. Through `settings.url` it anchors the absolute addresses Baseline generates: canonical links, sitemap entries, the structured data. Baseline also hands it to Eleventy's `HtmlBasePlugin`, which resolves the links inside your pages against it. Set it wrong and nothing breaks visibly, which is the annoying part: the site looks fine and tells search engines it lives at `localhost`.

`ELEVENTY_ENV` is the development-versus-production switch. Set to `production` it minifies CSS and drops the navigator page; the `build` script from the previous page sets it for you, which is what `cross-env` was installed for. On a deployed site both variables come from your host rather than from this file, which is why the file stays out of git.

Eleventy will start now. It will also render nothing at all, because there is still no content, which is what the next page is for.
