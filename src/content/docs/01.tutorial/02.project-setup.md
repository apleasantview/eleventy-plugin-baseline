Baseline has an opinion about where things live. `src/` for what you write, `dist/` for what gets built, and a handful of folders in between that it finds by name without being told. That opinion is why there is so little configuration later, and it is why this page comes before anything gets installed.

So we build the shape by hand first. It takes a minute, and afterwards every file in the rest of the tutorial has an obvious place to go.

---

## Make the folder

```bash
mkdir simple-baseline-site
cd simple-baseline-site
```

Everything from here happens inside that folder.

---

## Lay out the directories

This is the whole structure. Nothing in it is a placeholder: every folder gets used before the tutorial is over, and about half of the names are not yours to choose.

```text
simple-baseline-site/
  src/
    _data/              # site identity lives here
    _includes/
      layouts/          # the shell your pages render into
    assets/
      css/              # one CSS entry point
      js/               # one JS entry point
    content/
      pages/            # your Markdown
    static/             # copied to the site root untouched
```

One command makes all of it:

```bash
mkdir -p src/_data src/_includes/layouts src/assets/css src/assets/js src/content/pages src/static
```

That's bash. If your shell doesn't take `-p`, make them by hand from the tree above.

Now, which half is which. `_data`, `_includes`, `assets` and `static` are Baseline's: it ships a directory configuration that names them, and renaming one means telling Eleventy about it yourself. `content/` is yours entirely. Eleventy renders what it finds anywhere in `src/`, so the arrangement inside `content/` is a filing decision rather than a technical one, and `pages/` is just the first drawer.

`dist/` is missing on purpose. It appears the first time you build.

The one oddity is `static/`. On disk it is `static/`, but in templates and config Baseline calls it `public`, which is the name most site generators use. Two names, one folder. It only matters the day you go looking for it in the [[project-structure | project structure]] page.

## Keep the generated files out of git

If you are tracking this in git, add a `.gitignore` at the project root. Three lines, and one of them is for a file that does not exist yet:

```text
node_modules/
dist/
.env
```

The first two are rebuilt from what you commit, so there is nothing to gain by keeping them. `.env` arrives on the next page and holds the values that differ between your laptop and the live site. Ignoring it now means never having to remember to.

Not using git? Skip the file. Nothing else in the tutorial depends on it.

## Add the package file

Now the folder can become a project.

```bash
npm init -y
```

That writes a `package.json` full of defaults. Two things need adding, and the first one will save you a confusing error in about five minutes:

```json
{
	"name": "simple-baseline-site",
	"type": "module",
	"scripts": {
		"start": "rimraf dist/ && npx @11ty/eleventy --serve",
		"build": "rimraf dist/ && cross-env ELEVENTY_ENV=production npx @11ty/eleventy"
	}
}
```

`"type": "module"` tells Node that the `.js` files here are ES modules, written with `import` and `export`. Baseline is ESM and so is the config you are about to write. Without the line, Node reads `eleventy.config.js` as an older-style CommonJS file, stops at the first `import`, and tells you that you cannot use import statements outside a module. It is a one-line fix to an error that reads like a much bigger problem.

The two scripts are the only commands the rest of the tutorial needs: `npm start` for local development, `npm run build` for the production build. Both clear `dist/` first, for a reason that gets its own aside once there is something to build.

Both also lean on two small helpers that are not installed yet. That is the last step on this page.

---

## Install the packages

Three commands rather than one, so you can see what each is for.

```bash
npm install @11ty/eleventy @11ty/eleventy-img
```

Eleventy itself, and the image library. Baseline names both as peer dependencies: your project uses them directly too, so they belong in your `package.json` rather than buried in the plugin's.

```bash
npm install rimraf cross-env
```

The two helpers from the scripts above. `rimraf` deletes `dist/` the same way on every operating system, and `cross-env` sets `ELEVENTY_ENV=production` for a single command on Windows too, where a bare `NAME=value` prefix means nothing.

```bash
npm install @apleasantview/eleventy-plugin-baseline
```

And Baseline, which arrives with everything else it needs already inside it, PostCSS and esbuild included. That is why it is the shortest line of the three.

Nothing runs yet. There is no config telling Eleventy about Baseline, and nothing to render. Both arrive next.
